**DISMISSED** (considered, not defects):

1. **Truncated tool calls executing unsafely.** pi-agent-core refuses *all* tool calls from a length-truncated message (`agent-loop.js:120-127`, `failToolCallsFromTruncatedMessage` at `:263`) and records an error tool result. `beforeToolCall` (the policy barrier) is never reached, `budgets.noteToolCall` is not charged, and `toolCallsFromMessages` records `status: "error"`. No unsafe execution, no ACL or approval bypass. (The mid-JSON bypass is a separate finding, not a counterexample to this one.)
2. **Crash or unhandled rejection on the new error path.** Pushing `{type:"error"}` completes the AssistantMessageEventStream and resolves `result()` (`event-stream.js` `push` -> `resolveFinalResult`); `agent-loop.js:107-111` returns on `stopReason === "error"` without executing tools; the later `stream.end()` is inert. `run.ts` wraps every repair and coverage call in try/catch, `canRepair`/`canCover` re-check abort and wall time before each model call, and execute-turn wraps the whole turn. No unhandled rejection and no path that stores unvalidated prose.
3. **A truncated draft leaking through as unvalidated text.** Impossible: `enforce()` runs on every candidate, repair and coverage additions are kept only when `enforce(x) === x` (run.ts:527, 609, 646, 704), and each of those blocks re-checks `wall.aborted` and the abort signal before keeping the text.
4. **Uniform UNAVAILABLE breaking the eval harness, eval-run, or the live Northwind scorer.** It does not. `prose-to-structured.ts:36` maps all four host strings to `insufficient_evidence`, so the ephemeral path's `answer` and `structuredAnswer` are identical to what the old empty draft produced, `evidence` is unchanged, and `refusalReason` is unset in both cases, so `scoreNorthwindAnswer` sees the same row. `runManualEvaluations` catches throws and records a fail either way, so no shadow or bake-off comparison shifts.
5. **Approval resume depending on the old empty-draft behavior.** It never re-runs the model: `resumeApprovedAgentRun` (workers/brain/src/approval-resume.ts) only validates the binding and commits the stored pending call. Unaffected. (It is also *not* a caller of the new branch, which matters because the production persisted path never observes `finalResponse` for a failed turn.)
6. **Usage double counting across calls.** No. `prompt_tokens`/`completion_tokens` are per-request and each AssistantMessage carries only its own call's usage, so `assistantTokenTotals` summing is correct, not cumulative. The one deliberate over-count is prompt tokens across N calls (shared prefix counted N times), which is conservative; the harm is that the check is armed at all, which is the separate finding.
7. **Missing usage silently becoming zeros.** Acceptable and no worse than before: `usageNumber` returns 0 for absent, negative or non-finite values, the house pattern already zero-filled every usage object, and a provider that omits usage degrades to the previous unarmed-budget behavior rather than mis-accounting. Worth knowing, not a defect.
8. **`totalTokens: usageNumber(...) || input + output`.** Inert: a legitimate provider total of 0 with 0+0 yields the same 0, and `totalTokens` is read by no budget, metric or stored row (only `input`/`output` are).
9. **The first chat call exhausting the budget and making repair or coverage impossible.** It cannot. `assertTokenTotals` throws only on strictly `>`, so a single 4,000-token call passes, and repair and coverage are charged through `noteTurn` (run.ts:557, 596, 640, 688), never through tokens, so they stay available and are separately bounded by `modelTimeoutMs` and the remaining wall time. Only the multi-call case breaks, and that is covered.
10. **Usage cost fields left at zero.** Deliberate: no per-token cost accounting exists in the run, the model descriptor carries the rates, and Cloudflare bills the account. No budget, alert or stored row reads `usage.cost`.
